## Findings

### 1. Cloud Armor WAF never evaluated (fixed)
The per-IP throttle rule sat at priority 1000 with match `true`. Cloud Armor stops at the first matching rule, so every request was accepted by the throttle and the SQLi/XSS/LFI/RCE/protocol/scanner rules at 2000–2005 never ran. LB logs confirmed `outcome=ACCEPT priority=1000` for injection payloads.
**Fix:** throttle recreated at priority 5000 (same limits: 300 req/min/IP → 429), rule 1000 deleted. Verified: `' OR 1=1--`, `UNION SELECT`, `<script>`, `../../etc/passwd` now return **403** with `outcome=DENY priority=2000–2002`; a burst of 330 requests still yields 429s (16 of 330).

### 2. `/metrics` publicly readable (fixed)
Prometheus metrics (route names, provider counts, latency histograms, 431 lines) were served to anyone. Now behind the admin token whenever one is configured (production); regression test `TestMetricsRequireAdminInProduction`.

### 3. Supply-chain CI had never run (fixed)
`.github/workflows/supply-chain.yml` contained two unquoted `${{ }}` expressions inside YAML flow mappings, so GitHub rejected the file and every run since the workflow was added failed before any scanner executed. Quoted both; the workflow now runs and, on its first real execution, found:
- **govulncheck:** the KMS `AsymmetricSign` path reached a vulnerable http2 transport via `golang.org/x/crypto` 0.54 → upgraded to 0.55 (+ grpc 1.83.2). All Go packages still pass; coordinator rebuilt and redeployed (revision 00010).
- **pip-audit (security harness):** `cryptography` 46.0.0 had 4 advisories → 50.0.0; the 32 harness tests pass.
- **npm audit (site, webapp, console, demo):** `next` 15.1.6 (critical dev-server advisory), `postcss` 8.4.31 (high), `sharp` 0.33 (high) → next 15.5.25, sharp 0.35, postcss 8.5.28 with an npm override for the copy bundled inside next. Typecheck and production builds pass for all four; audit reports 0 vulnerabilities. Cloudflare Pages redeployed them.
- **gitleaks, cargo-audit:** clean.
The workflow is now green end to end.

### 4. Per-key rate limit
140 rapid `/v1/models` calls with one key → 130×200 then 10×429 with `Retry-After`; recovered after the window. Works as configured (120/min).

### 5. Capacity, not a bug
20 concurrent 40-token completions all succeeded but queued: TTFT p50 65 s, p95 108 s, max 108 s. Two devices, one job at a time each. Requests wait rather than fail; the quote engine's ETA already models this. More providers is the only fix.

### 6. CORS (observation)
Non-app origins receive `Access-Control-Allow-Origin: *` without credentials, which is the standard posture for a bearer-key API. Localhost origins are credentialed for local development; acceptable for now, revisit before GA.

## Desktop provider, public installer path
Ran `curl -fsSL https://api.ayni-ai.com/install/provider.sh | SC_REGISTRATION_TOKEN=… bash` as a brand-new user in an isolated directory.
- **Blocker found:** the GitHub repository is **private**, so the installer's prebuilt-binary download (`releases/download/provider-latest/…`) returns 404 to anonymous users and the script silently falls back to a from-source Rust build. The public site also links the repo as open source under Apache 2.0. Decision needed: make the repository public, or host the binaries on the public `models.ayni-ai.com` bucket (needs an R2 write token in CI).
- With the freshly built macOS binary pre-placed, the rest of the flow works: 491 MB model pulled from the signed registry, node registered as `community`, and with the other nodes paused it served demo jobs at ~90 tok/s on an M1 Pro.
- The served installer did not pin the coordinator's manifest key, so desktop nodes ran without signed-manifest verification. Fixed in code (`/install/provider.sh` now fetches `/v1/manifest-key` and runs with `SC_REQUIRE_MANIFEST=1`); ships with the next coordinator deploy. Download failures are no longer hidden.
- `release-provider.yml` used delete-then-create for the rolling release, leaving a window where installs 404; now uploads in place. A fresh build from `main` was dispatched.

## Coordinator deploy with the pinned-key installer (after gcloud re-auth)
Deployed revision 00014 → the served `/install/provider.sh` now pins the KMS signing key; a fresh public install logged `workload manifest verification enabled keys=1 require=true` and registered. The rollout exposed a hand-over gap: the serving revision was untagged, so the drain had no URL and the Mac node stayed stranded. `deploy.sh` now tags the serving revision (`prev-NNNNN`) before every rollout, drains it afterwards and removes the temporary tag; validated on revision 00017 (`drained: 1`, provider back in 10 s).
